# Coding Standards

> Generated by `/adopt` from the real project conventions (Expo Router + React
> Native + Redux Toolkit). Review and adjust anything that doesn't match your
> intent, then run `/overview`.

## TypeScript

- Strict mode enabled (`tsconfig.json`)
- No `any` types - use proper typing or `unknown`
- Define interfaces for all props, API responses, and data models
- Use type inference where obvious, explicit types where helpful
- Path alias `@/*` resolves to the project root (`import { colors } from '@/theme'`)

## React / React Native

- Functional components only (no class components)
- Use hooks for state and side effects; shared hooks live in `hooks/`
  (`useX` naming, exported from `hooks/index.ts`)
- Keep components focused - one job per component
- Extract reusable logic into custom hooks

## Routing (Expo Router v6)

- Route files under `app/` stay minimal and re-export a scene component:
  `export { Home as default } from '@/scenes/main';`
- Screens live in `scenes/<group>/` (`auth`, `main`, `onboarding`,
  `profile-verification`), not in `app/`
- Route groups: `(auth)` pre-login, `(details)` stacked detail/sub screens,
  `(main)` the post-login Tabs shell
- Dynamic routes for item/collection pages (`campaign/[id].tsx`, `order/[id].tsx`)

## File Organization

- Reusable UI: `components/elements/<ComponentName>/` with
  `<ComponentName>.tsx`, `index.ts`, and a co-located `<ComponentName>.test.tsx`
- Layout chrome (tab bar icons/labels, etc.): `components/layouts/`
- Screens: `scenes/<group>/<ScreenName>.tsx`
- Route files: `app/<route>.tsx` (thin re-export only)
- Redux slices: `slices/<feature>.slice.ts`, aggregated in `slices/index.ts`
- API calls: `services/<feature>.service.ts` - never call an API directly from
  a component
- Per-screen styles: `styles/<screenName>.ts` (camelCase, matches the screen)
- Types: `types/<feature>.ts` (PascalCase exports), aggregated in `types/index.ts`
- Mock data (placeholder until the backend exists): `data/<feature>.ts`
- Design tokens: `theme/` (colors, fonts, images, radius, shadows, spacing)
- Device/env helpers: `utils/deviceInfo.ts`, `utils/config.ts`

## Naming

- Components/Screens: PascalCase (`ItemCard.tsx`, `CampaignDetails.tsx`)
- Route files: kebab-case matching the URL segment
- Functions: camelCase
- Constants: SCREAMING_SNAKE_CASE
- Types/Interfaces: PascalCase (no prefix)

## Styling

- `StyleSheet.create` for all styles - no inline style objects, no CSS-in-JS
  library
- Styles live in a per-screen module under `styles/`, imported into the scene
- Colors, fonts, spacing, radius, and shadows come from `@/theme`, never
  hardcoded literals
- Automatic light/dark mode via `useColorScheme` (`hooks/useColorScheme.ts`);
  every screen must render correctly in both

## State Management

- Global state: Redux Toolkit slices under `slices/`, read/write through the
  project's slice hooks (e.g. `useAppSlice`) rather than raw `useSelector`/
  `useDispatch` where a convenience hook already exists
- Local state: component-local `useState`/`useReducer` when it isn't shared
  across screens
- Local persistence: AsyncStorage via the typed `useDataPersist` hook
  (`hooks/useDataPersist.ts`) - don't call AsyncStorage directly from
  components

## Data Fetching

- All API calls go through `services/` - components never call `fetch` or an
  HTTP client directly
- As real endpoints replace the current mock fixtures (`data/*.ts`), keep the
  same service-layer boundary so screens don't need to change when the data
  source does

## Error Handling

- No `console.log` left in production code
- Surface user-facing errors through the app's existing UI patterns
  (inline field errors, `ConfirmDialog`, etc.), not raw thrown errors

## Testing

A test runner is already configured: Jest (`jest-expo` preset) + React Native
Testing Library. `npm run test` is declared in the Commands section of
`AGENTS.md`, so **the opt-in switch is already on** - tests are a gate for
logic-bearing steps, not an optional extra.

No combined `Verify` command is declared yet (no `typecheck` script exists
alongside `test`/`lint`/`build`). Run `/ci` when you want one exact command
wired into an automatic GitHub check; until then, `format` -> `lint` -> `test`
already run on every PR/push via `.github/workflows/test.yml`.

- **What to test (the scope rule):** this project already deviates from the
  Blueprint default and tests reusable UI components directly (every
  `components/elements/<Name>/` ships a co-located `<Name>.test.tsx` via React
  Native Testing Library) as well as pure logic - parsers, formatters,
  validators, slice reducers, service functions. Keep following that existing
  pattern for new reusable components and logic.
- **What not to test:** full screen/scene integration (navigation between
  screens, real device APIs, anything requiring a real backend). Verify those
  with the dev server / Expo Go and manual evidence, not brittle integration
  tests.
- **The gate (when a runner is configured):** a build step that adds in-scope logic
  must ship a passing test in the same reviewable diff. The project's test command
  must be green before the step is approved, before any checkpoint commit, and
  before `/complete` merges. UI and integration-only steps are exempt and ride on
  screenshot plus build evidence.
- **When it's named:** the `/feature` spec's Testing section predicts the coverage,
  `/implement` writes the test with the step, and if a step surfaces logic the spec
  didn't foresee, add a focused test then.
- An empty suite should fail, not pass, so "no tests ran" never looks like "passed".
- Test files live next to source files (for example `feature.test.ts`).
- Run them via the project's test command (see Commands in `AGENTS.md`), not a
  hardcoded tool name.

Stack binding: this project uses Jest (`jest-expo` preset) with React Native
Testing Library, `jest.mock()` for external dependencies (AsyncStorage,
services), and `jest.useFakeTimers()` for time-dependent logic.

## Browser Verification

For UI and integration behavior, prefer real browser evidence over reading the
code and assuming it works.

- Browser automation is separately opt-in through `/browser-tests`. That setup
  reuses a compatible runner or prefers Playwright for supported projects, then
  documents the exact command as `Browser tests` in `AGENTS.md`.
- When `Browser tests` is declared, add focused coverage for stable behavioral
  done-whens when it is proportionate, and run the documented command during
  `/check`. Do not assume it proves visual fidelity, real authenticated-profile
  behavior, browser chrome, or another claim the test does not observe.
- If no Browser tests command is declared, do not add a runner silently in the
  middle of an unrelated feature. Use the available dev server, browser
  screenshots, build output, API output, or manual evidence instead.
- Browser tests are not part of the default Verify command or CI unless the user
  separately chooses that slower gate.
- Browser evidence is especially important for flows that click, type, submit,
  navigate, download files, render complex layouts, or depend on client-side
  state.

## Code Quality

- No commented-out code unless specified
- No unused imports or variables
- Keep functions under 50 lines when possible

## Comments

Write code that explains itself; comment only what the code cannot say.
Over-commenting is a common AI tell, so resist it.

- Comment the **why**, not the **what**. Delete any comment that restates the code.
- No banner/header blocks, section dividers, or step-by-step narration of obvious
  code. A file does not need a comment announcing each region.
- A comment earns its place only when it captures something the code can't: a
  non-obvious decision, a gotcha or workaround, why a value is what it is, or a
  link to a spec or issue.
- Prefer self-documenting names and small functions over explanatory comments.
- Keep doc comments minimal: a one-line purpose on an exported type or function is
  plenty; don't write JSDoc that just repeats the signature.
- When in doubt, leave the comment out.

## Writing

- No em dashes (U+2014) in generated content: docs, comments, commit messages,
  READMEs, specs. They read as AI-generated.
- Use a hyphen for `term - description` separators; rephrase prose with commas,
  parentheses, or a colon. Avoid en dashes and the ellipsis character too.
